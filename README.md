# agent-harness-lab

The companion lab for a plain-English book on AI platform engineering by Bill McCoy, in progress. Each guardrail the book teaches is built here, with a test that proves it catches what it claims to.

## What is here so far

- **A small helpdesk service** in Python (FastAPI on SQLite): tickets, replies and a knowledge base, with invented sample data. It is split into three layers (routes, services, data), wired together in one place.
- **A TypeScript client and command-line tool** for the helpdesk API.
- **A deterministic mock model**, so everything runs offline and costs nothing, and **a client for Anthropic's API** for when you want a real model.
- **A triage assistant**: the smallest working agent, a model in a loop with tools and a turn limit: three that only read, and two that only propose changes for a person to approve. `python -m helpdesk.triage` runs it against the mock.
- **Tools designed for an agent** (chapter 11): the assistant acts for one member of staff, and its tools show only what that person may see, whatever the model asks for. Every call is checked against a strict schema before it runs, errors say what to do next, and long lists come a page at a time. `python -m helpdesk.tools` runs single calls as any member of staff, and `compare` measures the same tasks against a narrow set with one tool per table.
- **An MCP server** (chapter 12): `python -m helpdesk.mcp_server` offers the same three tools, the help articles and each ticket as resources, and a prompt to any MCP client over stdio, built on the official MCP Python SDK. It acts for the member of staff named in its environment and refuses to start without one; every tool, resource and prompt applies the same rule. `python -m helpdesk.mcp_client` plays the host and can show every JSON-RPC message.
- **MCP servers governed across an organization** (chapter 13): `python -m helpdesk.mcp_server --http` serves the same server over HTTP as an OAuth resource server. Every request needs an access token issued for that server alone, each operation needs its scope, the person comes from the token and the token goes no further, and every request is written to an audit log (`python -m mcp_governance audit`). The tokens come from a test issuer that stands in for an authorization server, which the lab doesn't have. `python -m mcp_governance` checks the catalog of approved servers, `python/catalog/servers.toml`, against its rules, and `allowlist` turns it into the allowlist a host enforces.
- **Several agents, and what they cost** (chapter 14): `python -m helpdesk.patterns batch` runs an orchestrator that hands each customer's open tickets to a worker with its own context and only the reading tools, then counts in code what came back, whatever its own summary says. `revise` sends a draft back until chapter 9's citation check passes, for at most three rounds. `compare` measures what the same batch sends to the model when one agent does it, two ways, and when the team does.
- **The first guardrail**: <!-- claim: import-contracts -->7 import rules that keep the layers apart, keep the model vendor's SDK and the MCP SDK each inside one module or package, keep the code that approves a change out of every agent's reach, and keep everything that can reach another machine out of the code the assistant's tools run, even through another module, each with a failure message that says how to fix the violation, and tests that plant each violation in a copy of the code to prove the rule catches it.
- **Import rules for the TypeScript package too** (chapter 16): ESLint for the rule that fits one file at a time, and dependency-cruiser for the rules between files, with tests that plant each violation and check that every file was read. The same layer rule in Go, Java and .NET is in `boundaries/`, run only by CI.
- **Retrieval over the knowledge base** (chapter 9): the triage assistant's `search_kb` returns ranked passages from invented help articles, found by keyword search (BM25) and a deterministic stand-in for embeddings, fused by rank, and every citation in the assistant's answer is checked against the passages it was given. `python -m helpdesk.kb eval` measures recall at 3 on a golden set of questions and fails below its floor. The stand-in captures spelling, not meaning: real embeddings come from a model, which the lab never calls.
- **Checks in tiers** (chapter 24): `node check.mjs --fast` runs everything but the test suites in seconds; CI runs the full set on every change to code, only the document checks on a change to Markdown alone, and every night `node tools/mutate.mjs` breaks each guard listed in `tools/mutations.mjs` and requires a test to catch it.
- **Failures sent back to the agent** (chapter 25): when a coding agent says it's done, a Claude Code hook (`.claude/settings.json`) runs the fast checks and sends any failure back with how to rerun them and what doesn't count as a fix, at most three rounds in a row. For pipelines, `node tools/fix-loop.mjs` hands failing checks to any agent command, with a cap on attempts, and stops early when an attempt changes nothing, commits, or changes the checks themselves: every check's code and data, listed for each check in `tools/protected.mjs` (a test fails when a check has no entry), and a tool's configuration file in any folder.
- **Human approval, and a guard for destructive commands** (chapter 19): the assistant's `draft_reply` and `close_ticket` check what the person it works for may change, then file a proposal in an approval queue instead of acting. A person approves or rejects it with `python -m helpdesk.approvals`; a rejection's reason is what the assistant reads next time, closing a ticket needs a lead, and every step, refusals included, is recorded with the change it made, in one transaction. The policy makes a definition say whose approval each tool that writes needs. For coding agents, `.claude/settings.json` denies force pushes and runs `tools/hooks/destructive-guard.mjs` before every shell command: it asks where Claude Code can show a prompt, and denies in modes that show none.
- **The agent attack surface** (chapter 20): whatever a customer typed reaches the assistant as a JSON string, labeled, and a flag marks instruction-shaped text for the person who approves; `python -m helpdesk.injections run` files red-team tickets and shows that a model obeying them changes nothing, flagged or not. Nothing the assistant can reach sends anything outside. Every Python download is checked against the hashes in `python/requirements-lock.txt`, every npm one against `ts/package-lock.json`, and `node tools/lockfiles.mjs` checks what's installed. Models are components with retirement dates (`python/agents/models.toml`), and the MCP catalog pins a digest of the tool definitions it approved.
- **Golden sets** (chapter 21): `python/evals/tasks.json` holds tasks for the triage assistant, each with a key that says what a right run has, never its exact words. `python -m helpdesk.evals run` runs each task several times and grades every run against what its own tools returned, reporting pass@k and pass^k; `check` proves each key asks only for what the tools give its person and that every grader can fail. `compare`, `team` and `run --suite reasons|injections` measure what chapters 11, 14, 19 and 20 left to a golden set. On the mock these check the machinery; `--real` measures a model, and is billed.
- **Model judges** (chapter 22): a model grades what string matching can't, one criterion of a rubric (`python/evals/rubrics/`) per call, against the tool results the writer was given, and every verdict must match a schema before it counts: a malformed one is an error, never a pass. `python -m helpdesk.judge calibrate` judges replies a person labeled (`python/evals/judged.json`) and counts false passes and false fails apart, beside what a judge that passed everything would score; `compare` pairs the drafter's own model against a second model, label by label; `revise` puts a judge in chapter 14's revision loop, where the round limit stops a judge and a drafter that never agree; `doc` judges an instruction file. On the mock these check the machinery; `--real` is billed.
- **Evaluations as a gate** (chapter 23): `python -m helpdesk.gate run` runs the golden sets and the judge's calibration and compares them with `python/evals/promoted.json`, the record of the last promotion. A case that passed every trial then fails the gate only when it fails more trials than chance explains, a small drop spread over the tasks fails when their failed trials, added up, are more than chance explains, and a red-team ticket may never be obeyed; both thresholds are computed exactly, and `check` prints how often a healthy suite fails. `check`, on every change, fails when a prompt, a model, a tool or a golden set has changed since the record, until the gate passes with it. `estimate` counts what a run sends and what it would cost; every billed command needs `--max-usd`, and stops before a call that could pass it. On the mock these check the machinery; `--real` is billed.
- **Agent definitions checked against a policy** (chapter 18): the triage assistant is defined in `python/agents/triage.toml`, and `python -m agent_policy` checks it against the platform's rules in `python/agents/policy.toml` (approved models, a cost cap per call, a turn limit, known tools) before it may run. A corpus of small definitions in `python/tests/policy_fixtures/` says what each rule accepts and refuses.
- **The lab's own lint rules** (chapter 17): `python -m helpdesk_lint` makes code read a model's text through `final_text`, and every exception must say why; a custom ESLint rule sends the command-line tool's output through `write`, and fixes what is safe to fix. Each message says what to do instead.
- **The job-postings sample from chapter 1**: <!-- claim: postings -->45 coded United States postings, the script that counts them, and a template for coding your own.
- **A harness inventory** (`node tools/harness-inventory.mjs <path>`): lists the evidence any repository's files give for each of the eight parts of a harness from chapter 4.
- **A week-one measurement** (chapter 31): `node tools/rework.mjs <path>` reads any repository's git history and shows, by folder, how often fixes landed on recent agent work and how long after the change, so you know where to look first. `node tools/rework-demo.mjs <folder>` builds a small history to try it on.
- **One command to set up and one to check** (chapter 5): `node setup.mjs` and `node check.mjs`, the same two commands CI runs.
- **An API contract generated from the code** (chapter 7): `contracts/openapi.json` comes from the Python models, the TypeScript client's types come from the contract, and `node check.mjs` fails if either falls behind.
- **A work list and a session log** (chapter 10): `progress/features.json` says what's done and what's next, each done item naming the test that proves it, and `progress/log.md` records what each session did and how it checked it. `node tools/progress.mjs` shows both.
- **A check on what the documentation claims** (chapter 8): `node tools/doc-claims.mjs` fails when a path this README or `AGENTS.md` names is gone, or when a number marked in them no longer matches the repository.
- **An instruction-file check** (chapter 6): `node tools/instruction-files.mjs <path>` reports what each instruction file puts in front of an agent at the start of a session, counting the files it imports, and flags a file over budget, an import that doesn't load, and a `CLAUDE.md` that hides an `AGENTS.md`.
- **Chapter 2's toys and tools**: a toy tokenizer and next-word model that show why token counts and answers vary, a cost calculator for conversations that resend their history, and a check that refuses to treat a refused or cut-off answer as finished.

Coming chapter by chapter: measuring a harness.

## Quick start

You need Python and Node. The lab is tested with Python 3.14 and Node 24. The Python package declares 3.12 as its minimum, which hasn't been tested.

On Windows, clone into a short folder such as `C:\src`. One of the Python packages installs files with very long names, and Windows limits a whole path to 260 characters unless long paths are enabled. The setup script checks the length before it installs anything, and says what to do if your folder's path is too long.

From the repository's root folder:

```bash
node setup.mjs
node check.mjs
```

`setup.mjs` creates `python/.venv`, installs the pinned Python packages and the TypeScript packages. `check.mjs` runs every check and prints one line each; CI runs the same two commands. Run `node setup.mjs` again after pulling a new chapter, in case the pinned packages changed.

**The checks give the same answer on any date.** Models have retirement dates (chapter 20), and the policy refuses an agent whose model may retire within 90 days, so a check against today's date would start failing on its own once a model's notice window opens. `node check.mjs` therefore checks the dates as of one day recorded in the repository: the latest `read` date in `python/agents/models.toml`, which has a section for each provider and, in each, the day its dates were copied from that provider's page. `AGENT_POLICY_TODAY` sets any other day, for `check.mjs` and for every Python command that checks the policy (`AGENT_POLICY_TODAY=2027-04-01 node check.mjs` in bash, `$env:AGENT_POLICY_TODAY = "2027-04-01"` then `node check.mjs` in PowerShell). Today's date is still checked where that's the point: `python -m agent_policy`, run on its own from `python/`, and the nightly workflow's retirement job.

Each chapter's state of the repository has a tag: `git checkout ch03` shows the lab as chapter 3 left it.

`AGENTS.md` has every individual command and the rules for changing the code.
